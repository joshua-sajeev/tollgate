# TollGate

A gRPC-based rate limiter backed by Redis, implementing the token bucket algorithm with atomic Lua scripting.

## Status

Core rate-limiting pipeline — proto contract, Lua script, gRPC server, and CLI client — is implemented. The server validates request inputs and returns gRPC `InvalidArgument` for invalid user IDs or token costs. The end-to-end flow has been manually verified; automated tests and concurrency load testing are not yet included.

## Why this exists

TollGate is a personal learning project exploring distributed rate limiting with Go, gRPC, and Redis. It uses an atomic Redis Lua script to handle token-bucket operations (refill, check, and update), preventing race conditions when multiple concurrent requests or service instances share the same rate-limit state.

## How it works

### What I was trying to achieve

This is a learning project to understand how to handle gRPC in Go and the token-bucket rate-limiting algorithm.

### Major Components

- `docker-compose.yml` spins up a Redis server.
- `limiter.lua` is a Lua script that handles the actual token-bucket algorithm.
- `ratelimiter.proto` has the protobuf definition of my client and server — what they send each other, how they communicate.
- `gen/` contains the Go implementation of the ratelimiter proto, generated by `protoc`; we use the structs and methods in this folder throughout the rest of the project.
- `limiter.go` is responsible for wiring up Go and Redis — it calls `limiter.lua` via the created Redis client. Lua scripts execute as atomic operations, so even if concurrent requests arrive, each request is atomic at the Redis level.
- `cmd/server/main.go` starts a gRPC server, listens for clients, and calls the `limiter.go` functions which execute the Lua script.
- `cmd/client/main.go` handles client operations — it accepts CLI flags: the user ID, how many tokens this request needs, and some other optional parameters.

### Token Bucket Algorithm — limiter.lua

This is the main heart of the project. The script receives a Redis key built from the user ID (`ratelimit:<user-id>`), plus the capacity of the bucket, the refill rate (tokens added per second), and the request cost.

```lua
-- KEYS[1] = bucket key, e.g. "ratelimit:{identity}"
-- ARGV[1] = capacity      (max tokens the bucket can hold)
-- ARGV[2] = refill_rate   (tokens added per second)
-- ARGV[3] = cost          (tokens this request needs)
```

The script uses Redis server time as its clock, so all service instances use the same source of time. `TIME` returns `{seconds, microseconds}` as strings, so we combine them. Negative elapsed time is clamped to zero to handle clock changes:

```lua
local t = redis.call("TIME")
local now = tonumber(t[1]) + (tonumber(t[2]) / 1000000)
```

`HMGET` returns the values associated with the key — in this case the user ID — and gives back how many tokens are left and when the last refill happened. We only need to store the remaining tokens and the last refill time; from these we can calculate everything else and ensure consistency.

```lua
local bucket = redis.call("HMGET", key, "tokens", "last_refill")
local tokens = tonumber(bucket[1])
local last_refill = tonumber(bucket[2])
```

`elapsed` calculates how much time has passed since the last refill. `refilled` shows how many tokens have now been added (before accounting for the current request).

```lua
local elapsed = now - last_refill

local refilled = tokens + (elapsed * refill_rate)
if refilled > capacity then
	refilled = capacity
end
```

Only if there are enough tokens to serve the request do we reduce it and return allowed; otherwise we report how long to wait.

```lua
if refilled >= cost then
	remaining = refilled - cost
	allowed = 1
	retry_after = 0
else
	-- Deny, but the refill that happened is still real — persist it
	-- instead of leaving the bucket at its old, stale balance.
	remaining = refilled
	allowed = 0
	retry_after = (cost - refilled) / refill_rate
end
```

These values can be floating points with many digits. Remaining tokens is floored to an integer so we never report more than what's actually there, and `retry_after` is ceiled so the caller doesn't retry too early based on the result.

```go
return Result{
	Allowed:           allowed == 1,
	Remaining:         int32(math.Floor(remaining)),
	RetryAfterSeconds: int32(math.Ceil(retryAfter)),
}, nil
```

### limiter.go

The script is called using `redis.Eval` with the following values:

```go
func (l *Limiter) Check(ctx context.Context, userID string, cost int32) (Result, error) {
  ...
	values, err := l.redis.Eval(ctx, script, []string{"ratelimit:" + userID}, l.capacity, l.refillRate, cost).Slice()
  ...
	return Result{
		Allowed:           allowed == 1,
		Remaining:         int32(math.Floor(remaining)),
		RetryAfterSeconds: int32(math.Ceil(retryAfter)),
	}, nil
}
```

### server/main.go

When defining the server struct, say for now I only have one method, `CheckLimit` — if I add more methods later but haven't written their implementation yet, using `UnimplementedRateLimiterServer` means that calling any of those methods returns a "not implemented" error instead of a compilation error — i.e., forward compatibility.

```go
type server struct {
	pb.UnimplementedRateLimiterServer
	limiter *limiter.Limiter
}
```

## Configuration

The server reads its settings from environment variables (optionally via a `.env` file in the project root). Invalid or non-positive `CAPACITY` and `REFILL_RATE` values fall back to their defaults; unset variables also use defaults:

| Variable         | Purpose                                   | Default           |
|-------------------|--------------------------------------------|--------------------|
| `REDIS_ADDR`      | Redis address (`host:port`)               | `localhost:6379`  |
| `REDIS_PASSWORD`  | Redis password                            | *(empty)*          |
| `GRPC_ADDR`       | gRPC server listen address                | `:50051`           |
| `CAPACITY`        | Max tokens a bucket can hold              | `10`               |
| `REFILL_RATE`     | Tokens added per second                   | `5.0`              |

## Getting Started

```sh
# Configure a Redis password (required by docker-compose.yml), then start Redis.
export REDIS_PASSWORD=development-password
docker compose up -d

# start the gRPC server (in one terminal)
go run ./cmd/server

# fire requests at it (in another terminal; set the same Redis password for the server)
REDIS_PASSWORD=development-password go run ./cmd/server

# in a third terminal, fire requests at it
go run ./cmd/client -user-id alice -tokens 1 -n 10 -timeout 3s
```

The client requires `-user-id`, `-tokens`, and `-n` explicitly, even though defaults are declared for these flags. `-server` defaults to `localhost:50051` and `-timeout` defaults to `2s`. Run `go run ./cmd/client -h` to see all available flags and descriptions.
